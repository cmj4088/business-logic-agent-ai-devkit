# 系统架构 v5 — 从"能跑"到"能用"

## 前置反思

v4 犯了根本性错误：**用户每遇到一个问题，我就加一张表。** 68 张表不是在解决问题，是在把复杂度转嫁给用户。

v5 的核心原则：

> 用户不需要理解 68 张表。用户只需要理解"我现在该做什么"和"系统帮我做了什么"。

## 四、解决"Agent 可能骗我但我验证更累"

### 4.1 信任闭环

```
不是: "这里有5个中置信度标记，你去验证吧"
而是: "我已经自动验证了3个，1个在查，1个建议你关注"

文档中的标记逻辑改为：

🟢 已验证 — Agent已自动搜索确认（附来源链接），用户无需处理
🟡 验证中 — Agent正在搜索验证，预计3秒后出结果
🔴 需关注 — Agent无法自动验证，建议人类判断
         — 但Agent提供了替代方案和建议
⚪ 未检查 — 纯描述性内容，不需要验证
```

**一键重新查证**：
```
用户点"让Agent重新查证" →
Agent自动搜索 → 找到来源则升级为🟢 → 找不到则保持🔴并附说明
```

**信任累积**：
```
用户审核通过 MRD →
系统记录: 产品经理Agent 在"需求分析"任务中，所有🟢标记的事实事后验证正确率 100%
→ 下次该Agent的🟢标记直接展示为"历史100%准确"，用户可跳过
→ 如果正确率下降到 80%，系统主动提醒
```

### 4.2 推理摘要（不是推理链）

用户看到的不再是 240 行 reasoning_traces，而是：

```
┌───────────────────────────────────────────────┐
│ 💭 决策摘要：为什么建议砍掉无线充电功能          │
│                                                │
│ 参与讨论的 Agent：产品经理、研发、财务、市场      │
│ 讨论轮次：3 轮                                  │
│ 最终共识：砍掉（3票同意，1票反对）               │
│                                                │
│ 决策逻辑链：                                    │
│                                                │
│ ① 市场Agent → 目标用户对无线充电支付意愿约$5     │
│    🟢 基于200份问卷数据                         │
│                                                │
│ ② 研发Agent → 实现无线充电BOM成本增加$12         │
│    🟢 基于供应链Agent的报价                      │
│                                                │
│ ③ 财务Agent → ROI = ($5-$12)/$12 = -58%        │
│    结论：每卖一台亏$7                            │
│                                                │
│ ④ 产品经理Agent → 建议砍掉                       │
│    但保留硬件预留位置，未来成本下降后再加         │
│                                                │
│ 唯一反对：市场Agent认为无线充电是"卖点"           │
│ 但承认数据不支持                                 │
│                                                │
│ [展开完整推理链]  [导出为PDF]                    │
└───────────────────────────────────────────────┘
```

## 八、迁移策略

```
规则:
1. 每张表独立一个 migration 文件: db/migrations/001_create_users.sql
2. migration 文件名用序号 + 描述，不可修改已执行的 migration
3. 每次启动自动检查并执行未执行的 migration
4. 每个 migration 包含 up（执行）和 down（回滚）
5. 生产环境 migration 前自动备份数据库
6. CI 中跑 migration 测试：创建空库 → 执行所有 migration → 验证 schema 一致性
```

## 九、v5 核心原则总结

| 原则 | 之前（v4） | 现在（v5） |
|------|-----------|-----------|
| 展示什么 | 所有数据 | 用户需要处理的 + 系统自动完成的 |
| 启动流程 | 3 个问题 → 90% 默认值 | 5 必填快速启动 + 侧边栏持续配置 |
| 阻塞处理 | stuck_flag = 1 | 原因 + 影响 + 一键操作 |

| 推理 | 240 步推理链 | 自然语言摘要 + 可选展开 |
| 审核 | 逐个项目点 | 审核仪表盘 + 批量操作 + 邮件快速操作 |
| 配置修改 | 不知道能不能改 | 明确的作用范围和影响预览 |

| 数据库 | 表数量见 database-schema-v3.md | 当前定义 18 张核心表（以 schema 文档为准） |

## 十一、测试策略（v5 新增）

> **审查发现**：v4 及之前版本完全没有测试策略。这是致命缺陷。v5 必须包含最低限度的测试覆盖。

### 11.1 测试分层

| 层级 | 覆盖范围 | 工具 | 最低覆盖率 |
|------|---------|------|-----------|
| 单元测试 | 数据库 schema 约束、工作流引擎状态机、Agent 提示词渲染、插件 manifest 校验 | pytest | 80% |
| 集成测试 | API 端点 + 数据库、Agent 轮次编排 + 消息流、WebSocket 连接生命周期 | pytest + httpx | 60% |
| E2E 测试 | 完整项目生命周期（概念→发布）、多 Agent 辩论场景、插件安装→调用→卸载 | Playwright | 关键路径 100% |
| 安全测试 | Prompt Injection、文件上传、SSRF、XSS、SQL 注入 | pytest + 安全文档测试用例 | 所有已知向量 |

### 11.2 测试优先实现顺序

1. **数据库迁移测试**：创建空库 → 执行所有 migration → 验证 schema 一致性
2. **API 端点冒烟测试**：每个端点的 200/401/404 响应
3. **Agent 提示词渲染测试**：给定 IPDContext → 验证输出包含必要字段
4. **工作流引擎状态机测试**：阶段推进、门禁投票、回退路径

### 11.3 CI 要求

- 每次 PR 必须通过数据库 migration 测试
- 每次提示词变更必须通过渲染测试
- 每次 API 变更必须通过端点冒烟测试
- 发布前必须通过完整 E2E 测试（lite 模式概念阶段完整流程）

## 十二、LLM 成本模型（v5 新增）

> **审查发现**：文档完全没有成本估算。一个 standard 项目可能耗费 $15-30 的 LLM 费用，这直接影响定价策略。

### 12.1 成本估算公式

```
项目总成本 ≈ Σ(活动数 × 平均轮次 × 参与Agent数 × (prompt_tokens + completion_tokens) × 模型单价)
```

### 12.2 典型项目估算（Claude Sonnet 定价）

| 模式 | 活动数 | 估算 Token | 估算成本 |
|------|--------|-----------|---------|
| lite | 24 | ~200 万 | $8-12 |
| standard | 31 | ~350 万 | $12-20 |
| full | 34 | ~500 万 | $18-30 |

> 注：以上为粗略估算。实际成本应在首个真实项目运行后校准。系统提示词是固定成本（每 Agent 约 2000-5000 token/轮），优化提示词长度可显著降低成本。

### 12.3 成本控制策略

- 系统提示词精简：每角色核心提示词控制在 1500 token 以内
- 低复杂度任务使用便宜模型（如竞品分析初稿用 Haiku）
- Prompt Injection 检测使用最便宜模型（Haiku），且仅对用户直接输入执行
- 提供用量仪表盘：用户可实时查看项目 LLM 花费

## 十三、产品定位澄清（v5 新增）

> **审查发现**：文档在"桌面应用"和"SaaS 平台"之间摇摆。API 设计了 B2B 多租户/SSO/GDPR，但数据库用 SQLite，安全用桌面应用方案。

### 13.1 明确决策：桌面应用优先

- **第一阶段（MVP）**：单用户桌面应用（Electron + 本地 FastAPI + SQLite）
- **第二阶段（评估）**：收集 50+ 用户反馈后评估 SaaS 需求
- **第三阶段（可选）**：如果 SaaS，需替换 SQLite → PostgreSQL，增加多租户隔离

### 13.2 MVP 功能边界

| 包含（P0） | 推迟（原 P1-P3） |
|-----------|-----------------|
| 单项目 IPD 流程 | SSO 单点登录 |
| 6 Agent 协作 | B2B 多租户/组织管理 |
| 基础审核流程 | GDPR 数据导出/删除 |
| 内置工具（硬编码） | 插件市场 |
| 本地 SQLite 存储 | Webhook 回调 |
| WebSocket 实时推送 | 演示项目 |

### 13.3 单人模式

MVP 提供"单人模式"：用户独自使用 6 个 Agent 时，所有审核/投票/门禁自动通过。Agent 产出直接标记为"自动完成"。用户可随时切换到"团队模式"启用审核流程。

## 十四、未来交互模式预留：群聊驱动

**核心思路**：把整个项目做成一个群聊，Agent 就是群成员，阶段 = 话题，门禁 = 群投票，产出物 = 群文件。

**预留位置**：
- `messages` 表已支持 `sender` 字段区分 human/agent
- `agent_rounds` 的并行/串行/辩论轮次可直接映射为群聊中的讨论
- WebSocket 流式输出天然适配群聊实时消息

**不做现在**，等基础流程跑通后再作为第二种交互模式（模式B）接入。当前优先做模式A（流程驱动看板）。
